# CS-003: Suspicious Sudo Activity

## Что это за инцидент

Пользователь `testuser` с ограниченными правами sudo попытался выполнить
серию запрещённых команд с повышенными привилегиями:
заглянуть в `/etc/shadow`, открыть root-оболочку, отредактировать sudoers.

Wazuh зафиксировал эти попытки и создал алерты, потому что **сам факт
обращения к запрещённым командам** — это тревожный сигнал. Пользователь
либо ошибся, либо что-то ищет.

## Основные данные

| Параметр | Значение |
|---|---|
| Дата | 2026-10-09 |
| Жертва | Debian 13 (192.168.0.9) |
| Подозрительный пользователь | `testuser` (ограниченные sudo-права) |
| Уровень критичности | High (Level 10) |
| MITRE ATT&CK | T1548.003 — Abuse Elevation Control Mechanism: Sudo |
| Доп. тактики | Privilege Escalation, Discovery |
| Статус | Закрыт, компрометации нет |

## Что произошло

В лаборатории был создан тестовый пользователь `testuser`. Ему выдали
sudo-права **только на две команды**: `ls` и `cat`. Это реалистичная
ситуация: часто в компаниях дают ограниченный sudo, а не полный.

Дальше `testuser` выполнил серию действий, которые выглядели как
**разведка и попытка эскалации привилегий**:

1. **Посмотрел, что ему разрешено** — `sudo -l`. Это типичное
   действие при попытке понять, как получить больше прав.

2. **Попробовал прочитать `/etc/shadow`** — файл с хэшами паролей.
   `sudo cat /etc/shadow`. Команда `cat` разрешена, но `/etc/shadow`
   защищён — sudo отклонил запрос.

3. **Попробовал открыть root-оболочку** — `sudo su -`. Запрещено.

4. **Попробовал отредактировать sudoers** — `sudo visudo`. Тоже
   запрещено. Это была бы попытка **дать себе больше прав**.

Все запрещённые команды были отклонены sudo.

## Что заметил Wazuh

Wazuh сгенерировал несколько алертов:

| Rule ID | Level | Что означает |
|---|---|---|
| 5402 | 3 | Успешное выполнение sudo от root |
| **5403** | **4** | **Пользователь впервые выполнил sudo** |
| **5405** | **10** | **Пользователь попытался выполнить запрещённую sudo-команду** |
| 5501 | 3 | Открытие PAM-сессии |
| 5502 | 3 | Закрытие PAM-сессии |

**Правило 5403** важно тем, что оно срабатывает при **первом** sudo
от пользователя. В реальной среде это триггер: «А этот человек вообще
должен пользоваться sudo?»

**Правило 5405** — самое серьёзное. Оно срабатывает, когда пользователь
пытается выполнить команду, которая **не разрешена** в его sudo-правах.
Уровень 10 означает, что это требует внимания аналитика.

## Доказательства

Из лога `/var/log/auth.log` на Debian:

```
sudo: testuser : command not allowed ;
TTY=pts/0 ; PWD=/home/testuser ;
USER=root ;
COMMAND=/usr/bin/cat /etc/shadow
```

Здесь видно всё:
- **кто** — `testuser`
- **что пытался** — `cat /etc/shadow`
- **от чьего имени** — `root`
- **из какой директории** — `/home/testuser`
- **результат** — `command not allowed`

Поля в алерте, на которые стоит смотреть:
- `data.srcuser` = `testuser` — кто выполнял
- `data.dstuser` = `root` — от чьего имени
- `full_log` — полная команда

## Хронология (UTC)

| Время | Событие |
|---|---|
| 00:09:58 | Первое выполнение sudo от `testuser` (rule 5403) |
| 00:09:58 | Попытка `sudo cat /etc/shadow` — отклонено (rule 5405) |
| 00:09:58 | Попытка `sudo su -` — отклонено (rule 5405) |
| 00:09:58 | Попытка `sudo visudo` — отклонено (rule 5405) |

Все события произошли в течение **одной секунды**. Это важно: одно
запрещённое действие можно списать на ошибку, но **четыре подряд** —
это уже поведение, которое нужно расследовать.

## Что я сделал

1. **Проверил, легитимны ли действия.** В лаборатории это была моя
   тестовая активность. В реальной среде — первый вопрос был бы:
   «Это testuser сам, или кто-то получил его доступ?»

2. **Проверил, не удалось ли обойти защиту.** Все команды были
   отклонены, ни одна не выполнилась. Проверил `/etc/sudoers` — не
   изменялся.

3. **Проверил сессии.** Команды `who` и `w` показали, что `testuser`
   заходил только с локальной консоли, без SSH.

4. **Проверил, нет ли других похожих событий.** В `auth.log` не было
   успешных sudo-сессий от `testuser` с более широкими правами.

5. **Эскалация не требуется.** Инцидент закрыт на L1.

## Рекомендации

Что стоит сделать, чтобы защититься от таких ситуаций:

| Приоритет | Что сделать |
|---|---|
| 🔴 Важно | Настроить алертинг на `rule 5405` — уведомление в реальном времени |
| 🔴 Важно | Проверять первых пользователей, использующих sudo, вручную |
| 🟡 Полезно | Ограничить sudo до **конкретных команд с конкретными аргументами** — например, `cat /var/log/syslog`, а не просто `cat` |
| 🟡 Полезно | Включить `auditd` для детального логирования sudo-команд |
| 🟢 Опционально | Ввести review sudo-прав раз в квартал |
| 🟢 Опционально | Автоматически уведомлять владельца учётки о подозрительной активности |

Инцидент показывает важный принцип: **не каждое подозрительное событие
означает атаку**. Иногда это ошибка пользователя, иногда — разведка.
Задача L1 — собрать факты и передать дальше, если нужно.

## Чему я научился

1. **Правило 5405 — важнее, чем кажется.** Оно ловит не «отказ в
   доступе», а **намеренную попытку** выполнить запрещённую команду.
   Это уже активное действие, а не пассивная ошибка.

2. **Контекст решает.** Одна запрещённая команда — случайность. Четыре
   подряд — паттерн. Именно на паттерны и нужно смотреть.

3. **Полный текст команды в логе — золото.** Без `full_log` я бы не
   знал, что именно пытался сделать `testuser`. Это ключевая информация
   для триажа.

4. **Sudo с ограничениями — хорошая практика.** Даже если пользователя
   скомпрометируют, он не получит полный root. В моём сценарии это
   спасло систему от эскалации.
