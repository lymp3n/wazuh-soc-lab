# CS-001: SSH Brute-Force

## Что это за инцидент

Кто-то пытался подобрать пароль к серверу Debian по SSH.
Атака шла с машины Kali Linux (это наша тестовая «атакующая» машина).
Wazuh заметил атаку и создал алерт.

## Основные данные

| Параметр | Значение |
|---|---|
| Дата | 2026-10-08 |
| Жертва | Debian 13 (192.168.0.9) |
| Атакующий | Kali Linux (192.168.0.11) |
| Уровень критичности | High (Level 10) |
| MITRE ATT&CK | T1110.001 — Password Guessing |
| Статус | Закрыт, компрометации нет |

## Что произошло

С машины Kali была запущена утилита `hydra`, которая подбирает пароли
методом перебора. Она пыталась угадать пароль пользователя `root`
на Debian через SSH.

Всего было сделано больше 1000 попыток входа. Все они оказались
неудачными, потому что в настройках SSH на Debian вход под `root`
по паролю запрещён (`PermitRootLogin prohibit-password`).

## Что заметил Wazuh

Wazuh среагировал на серию неудачных попыток входа и сгенерировал
несколько алертов. Самые важные:

| Rule ID | Level | Что означает |
|---|---|---|
| 5760 | 5 | Каждая неудачная попытка SSH-входа |
| 5557 | 5 | Ошибка проверки пароля |
| 5758 | 8 | Превышено максимальное число попыток |
| **5763** | **10** | **Обнаружен брутфорс SSH** — главный алерт |

**Правило 5763** — это главное. Оно сработало не сразу, а когда
Wazuh накопил достаточно событий и понял: «это не случайность,
это целенаправленный перебор паролей».

## Доказательства

Из лога `/var/log/auth.log` на Debian:

```
Failed password for root from 192.168.0.11 port 53710 ssh2
```

Поля, которые важно смотреть в алерте:
- `data.srcip` = `192.168.0.11` — откуда атака
- `data.dstuser` = `root` — кого пытались взломать
- `full_log` — полная строка события

## Хронология (UTC)

| Время | Событие |
|---|---|
| 22:09 | Первая неудачная попытка входа |
| 22:10 | Превышено максимальное число попыток |
| 22:14 | Атака продолжается, счётчик событий растёт |
| **23:05** | **Сработало правило 5763 — брутфорс обнаружен** |

## Что я сделал

1. **Проверил источник атаки.** IP `192.168.0.11` — это наша
   Kali Linux, тестовая машина. Атака ожидаемая, в рамках лаборатории.

2. **Проверил, не сломали ли систему.** Поискал в логах успешные входы:
   ```
   grep "Accepted password" /var/log/auth.log
   ```
   Успешных логинов с этого IP **не найдено**.

3. **Проверил активные сессии.** Команды `who` и `w` показали только
   мою учётку — посторонних подключений нет.

4. **Проверил настройки SSH.** Убедился, что вход под `root` по паролю
   запрещён — поэтому атака и не могла сработать.

5. **Эскалация не требуется.** Инцидент закрыт на L1.

## Рекомендации

Что стоит сделать, чтобы защититься от таких атак в реальной среде:

| Приоритет | Что сделать |
|---|---|
| 🔴 Важно | Установить `fail2ban` — он будет блокировать IP после нескольких неудачных попыток |
| 🔴 Важно | Отключить вход по паролю, использовать SSH-ключи |
| 🟡 Полезно | Ограничить список пользователей, которым разрешён SSH (`AllowUsers`) |
| 🟡 Полезно | Настроить уведомления в Telegram/Slack на алерт 5763 |
| 🟢 Опционально | Изменить стандартный порт SSH — снижает шум в логах |

Атака была успешно обнаружена Wazuh. Система не пострадала благодаря

## Чему я научился

1. **Композитные правила работают.** Wazuh не паникует на каждую
   отдельную попытку входа, а ждёт, пока накопится критическая масса.
   Только тогда срабатывает алерт высокого уровня.

2. **Простая защита работает лучше всего.** Запрет входа root по
   паролю сделал 1000+ попыток полностью бесполезными.

3. **Без сбора логов нет детекта.** Если бы я не настроил сбор
   `auth.log` через rsyslog, Wazuh бы ничего не увидел.

4. **Важно проверять факт компрометации.** Мало увидеть алерт —
   нужно убедиться, что атакующий не смог войти.
